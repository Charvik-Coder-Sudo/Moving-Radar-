# MSDF Display — C++17/20 + Qt6 architecture design

**Status: design document. No C++ implementation exists yet and none is to be written from this
document until it has been reviewed.** Nothing in the current Python application, the RDP or the
radar code changes because of it.

This describes how the display documented in [MSDF_DISPLAY_ARCHITECTURE.md](MSDF_DISPLAY_ARCHITECTURE.md)
would be built as a native C++ application: the type system, the modules, the threading and
rendering choices, what maps to what, and in which order it would be built.

---

## 1. Purpose and status

The Python application is the reference behaviour. A C++ port would be undertaken for three
reasons only: a lower and more predictable frame cost, a single deployable binary without a
Python environment, and compile-time enforcement of the unit and frame conventions that are
currently enforced by documentation and tests. It is **not** an opportunity to change what the
display shows.

Acceptance for any port: the same scenario and the same recorded packet stream produce the same
numbers on screen (positions to 1e-6 m, angles to 1e-9 rad) and the same states (LIVE / STALE /
HIDDEN) at the same times.

## 2. Scope and non-goals

In scope: the display application — export loading, packet reception, track lifetime, geometry,
3D / 2D / PPI rendering, interaction, panels, configuration.

Non-goals: rewriting the RDP or any part of MultiTrack; changing the packet layout; changing the
Scenario Export format or its generation; adding detection, association or fusion logic; a
network protocol of our own; a plug-in system; cross-platform UI beyond what Qt gives for free.

## 3. Fixed constraints

1. `D:\Moving Radar\MultiTrack` is **read-only**: not linked, not built against, not written to.
   The C++ display receives UDP datagrams and nothing else.
2. The Scenario Export is opened read-only; required files are never deleted or regenerated by
   the display.
3. No value is invented. Absent fields are modelled as `std::optional` and rendered as
   unavailable — never defaulted to zero.
4. The rotation equations are the project's own; they are transcribed, with the Python
   implementation and its tests as the reference.
5. Anything derived by the display is labelled as derived in the UI, exactly as today.

## 7. Build system

* One static library target per directory (`msdf_core`, `msdf_export`, `msdf_rdp`,
  `msdf_processing`, `msdf_app`, `msdf_render`, `msdf_ui`) and one executable.
* `target_link_libraries` expresses the layering of §9; a cycle is a build error, not a review
  comment.
* Qt features enabled per target (`AUTOMOC`, `AUTOUIC` only where needed).
* Presets: `windows-debug`, `windows-release`, `windows-asan`, `linux-release`.
* Test targets registered with CTest; `ctest --preset windows-debug` is the gate.

## 8. Architectural overview

```
   Scenario_Export files            UDP 127.0.0.1:9000
            │                                │
   ExportLoader (worker)            UdpReceiver (worker thread)
            │  ScenarioData                  │  std::vector<SystemTrackPacket>
            ▼                                ▼
   ScenarioProcessor  ──────────►  TrackStore  ──►  TrackProjector
            │  FrameState                         │  placed TrackViews
            └──────────────┬──────────────────────┘
                           ▼
                    AppState (one owner of everything shown)
                           │ Qt signals
        ┌──────────┬───────┴────────┬────────────┬──────────────┐
      View3D     View2D         AircraftPpi   TrackTable    StatusBar
```

Same shape as the Python application deliberately: one receiver, one store, one cached export,
one state object, views that only draw.

## 9. Layering rules

```
core      ← export, rdp, processing, render
export    ← processing, app
rdp       ← processing, app
processing← app
app       ← ui, render
render    ← ui
```

Rules: `core` has no Qt types in its public headers; `export` and `rdp` do not include `render`
or `ui`; a view never reads a file or a socket; all mutation goes through `AppState`.

## 10. Threading model

| Thread | Owns | Communicates by |
|---|---|---|
| GUI | every widget, `AppState`, `TrackStore`, timers | direct calls |
| `UdpReceiver` (`QThread` with its own event loop) | `QUdpSocket` | `emit batchReady(std::shared_ptr<const std::vector<SystemTrackPacket>>)`, queued |
| Export loader (`QtConcurrent::run` + `QFutureWatcher`) | file handles, parse buffers | `QFuture<ExportResult>` |

Data crossing a thread boundary is either a value type or a `shared_ptr<const T>`; nothing
mutable is shared, so there are no mutexes in the design. `Q_DECLARE_METATYPE` +
`qRegisterMetaType` for the payload types.

## 11. Memory and ownership

* Widgets: Qt parent/child ownership, raw observing pointers.
* Domain data: values and `std::shared_ptr<const>` snapshots; a `FrameState` handed to the views
  is immutable.
* Large arrays: `std::vector` with reserved capacity, or `Eigen::Matrix<double, Dynamic, 3>` for
  trajectories; no per-frame allocation in the render path (§36 budget).
* Track histories: fixed-capacity ring buffers (`boost::circular_buffer` equivalent written in
  `core`, capacity `rdp.trail_points`).

## 12. Error handling policy

* Recoverable, expected failures (a malformed packet, a missing optional file) →
  `std::expected<T, Error>` (or `tl::expected` on C++17), never exceptions.
* Programming errors → assertions, active in debug and in CI.
* Unrecoverable start-up failures (required export file missing) → an `ExportError` propagated to
  the UI and displayed; the application stays alive with empty world views.
* No exception ever crosses a thread boundary; the worker converts it to an error value first.

```cpp
struct PacketError { enum class Reason { Length, SensorCount, Numeric, Decode }; Reason reason; std::string detail; };
using DecodeResult = std::expected<SystemTrackPacket, PacketError>;
```

## 13. Units and strong types

The single largest source of defects in this domain is a silent unit or frame mix-up, so units
are types, not comments:

```cpp
namespace units {
template <class Tag> class Quantity {           // trivially copyable, constexpr
 public:
  constexpr explicit Quantity(double v) : v_(v) {}
  constexpr double value() const noexcept { return v_; }
  // +, -, *scalar, /scalar, comparisons; no implicit conversion to double
 private:
  double v_;
};
struct MetreTag {};  struct SecondTag {};  struct DegreeTag {};  struct RadianTag {};
using Metres  = Quantity<MetreTag>;
using Seconds = Quantity<SecondTag>;
using Degrees = Quantity<DegreeTag>;
using Radians = Quantity<RadianTag>;
constexpr Radians toRadians(Degrees d) noexcept;
constexpr Degrees toDegrees(Radians r) noexcept;
}
using Milliseconds = std::chrono::duration<double, std::milli>;   // export timestamps
```

The export's canonical `t_ms` and the packet's seconds therefore cannot be added by accident.

## 14. Geometry primitives

```cpp
using Vec3 = Eigen::Vector3d;
using Mat3 = Eigen::Matrix3d;

struct Pose {                       // position + orientation of a frame in the world
  Vec3 position;                    // ENU metres
  Mat3 rotation;                    // frame -> world
  Eigen::Affine3d toAffine(double scale = 1.0) const;   // x_world = p + scale * R * x_local
};
```

`Pose::toAffine` is the exact counterpart of `attitude.homogeneous`, and the scale multiplies the
rotation block only.

## 15. Frames as compile-time tags

A point carries the frame it is expressed in, so a mistake becomes a compiler error:

```cpp
struct WorldEnu {};  struct BodyFrd {};  struct RadarFrd {};  struct RdpState {};

template <class Frame> struct Point { Vec3 v; };
using WorldPoint = Point<WorldEnu>;
using BodyPoint  = Point<BodyFrd>;
using RadarPoint = Point<RadarFrd>;

template <class From, class To> struct Rotation { Mat3 m; };     // From -> To
using BodyToWorld  = Rotation<BodyFrd,  WorldEnu>;               // R_WB
using RadarToBody  = Rotation<RadarFrd, BodyFrd>;                // R_BR
using RadarToWorld = Rotation<RadarFrd, WorldEnu>;               // R_WR

template <class A, class B, class C>
Rotation<A, C> operator*(Rotation<B, C> lhs, Rotation<A, B> rhs);   // R_WR = R_WB * R_BR
template <class From, class To>
Point<To> operator*(Rotation<From, To> r, Point<From> p);
```

`RadarToWorld r; WorldPoint p; r * p;` does not compile. This is the compile-time version of what
[COORDINATE_AND_ATTITUDE.md](COORDINATE_AND_ATTITUDE.md) currently enforces by review and tests.

## 16. Attitude module (`core/attitude.h`)

```cpp
BodyToWorld  bodyToWorld(Degrees yaw, Degrees pitch, Degrees roll);   // T_ENU<-NED * Rz * Ry * Rx
RadarToBody  radarToBody(Degrees yaw, Degrees pitch, Degrees roll);   // mounting
struct Ypr { Degrees yaw, pitch, roll; };
Ypr          frdToYpr(const Mat3& frameInWorld);                      // == Ownship.Radar_Angles
```

Written out element by element exactly as the Python version, with a test comparing it to
`T_ENU←NED · Rz · Ry · Rx` built from Eigen `AngleAxisd`, and the eight attitude cases of §9 of
the coordinate document ported one to one.

## 17. Coordinates module (`core/coordinates.h`)

`wrap360`, `wrap180`, `frdDirection(az, el)`, `worldToFrame`, `frameToWorld`,
`radarMeasurements(L) -> {range, azimuth, elevation}`, `relativeRaeEnu(origin, point)`,
`convexHull2d(span<const Eigen::Vector2d>)`. Batch overloads take `std::span` and write into a
caller-provided output span so the render path allocates nothing.

## 18. Kinematics module (`core/kinematics.h`)

`speed`, `horizontalSpeed`, `headingFromVelocity`, `flightPathAngle`,
`estimatedBank(speed, yawRate)`, `predictCoordinatedTurn(...)` and:

```cpp
struct AttitudeCheck {                  // recorded vs what the recorded velocity implies
  Degrees yaw, pitch, roll;             // recorded, never modified
  std::optional<Degrees> headingFromVelocity, flightPathAngle;
  std::optional<Degrees> yawMinusHeading, pitchMinusFlightPath;   // the latter is the AoA
  std::optional<Degrees> estimatedBank;                           // coordinated turn, NOT measured
  std::string rollSource;
};
```

`std::optional` is what keeps "unknown" from becoming 0.0 on screen.

## 20. Export loader and parsing

Memory-map each CSV (`QFile::map`), split lines with `std::string_view`, parse numbers with
`std::from_chars` / fast_float. The files are hundreds of megabytes, so the loader:

* resolves the header once and keeps column indices;
* decimates to `display_rate_hz` while parsing, keeping recorded rows (no interpolation);
* reserves capacity from the file size estimate;
* reports progress by byte offset;
* collects `ExportIssue`s instead of throwing, and fails only on a missing required file.

Expected gain over pandas: parsing is I/O bound rather than allocation bound; the Python cold
parse is the dominant start-up cost today.

## 21. Binary cache format

Replaces the npz cache with a flat little-endian file per source, `cache/<stem>.<kind>.bin`:

```
magic "MSDFC1", uint32 version, uint64 sourceSize, uint64 sourceMtimeNs,
uint32 rows, uint32 cols, char kind[16], then rows*cols doubles (column-major)
```

Validity check is the same rule as today: source size **and** modification time must match, else
re-parse. The file can be `mmap`ed straight into an `Eigen::Map`, so a warm start does almost no
work.

## 24. RDP packet decoding

No `reinterpret_cast` over a struct: the layout is big-endian and packed, so decoding is explicit
byte reading, which is also what makes it portable and testable.

```cpp
inline constexpr std::size_t kPacketSize = 436;
inline constexpr int kMaxSensors = 4;
struct SystemTrackPacket {
  std::int32_t systemTrackId; double time; std::int32_t latestSensor;
  std::array<double, 10> fused;
  std::int32_t numSensors;
  std::array<std::int32_t, 4> sensorIds;
  std::array<std::array<double, 10>, 4> sensorStates;
  double receivedWall; std::string sender;
};
DecodeResult decode(std::span<const std::byte> datagram, double receivedWall, std::string sender);
```

Validation is exactly today's: size, `numSensors` in 0..4, all values finite. `std::byteswap`
(C++23) or a small `beRead<T>` helper handles endianness.

## 25. UDP receiver

`QUdpSocket` on a dedicated `QThread` with its own event loop: `readyRead` drains
`pendingDatagramSize`/`readDatagram` into a batch (cap 500), decodes each, and emits the batch.
This keeps the blocking-read semantics of the Python worker without a manual timeout loop.
`QAbstractSocket::error` maps to the `UDP UNAVAILABLE` state, retried on a 2 s timer. The socket
is bound, never connected, and nothing is written to it.

## 26. Track store and lifetime

```cpp
class TrackStore {
 public:
  bool ingest(const SystemTrackPacket&);        // false when ignored as a stale packet
  void reject(PacketError, double wall, std::string sender);
  bool tick(double nowWall);                    // ACTIVE / STALE / HIDDEN, true if changed
  std::vector<TrackView> views(double nowWall) const;
  Stats stats(double nowWall) const;
};
```

`std::unordered_map<std::int32_t, TrackRecord>` with the same thresholds
(`stale_timeout_s`, `stream_stale_timeout_s`, `hide_timeout_s`) and the same restart rule.
Statistics carry counts by rejection reason and a measured packet rate over a sliding window.

## 27. Track projection

One free function plus a small cache, mirroring `track_projection.py`:

```cpp
RadarPoint rdpToFrd(double x, double y, double z) noexcept { return RadarPoint{{y, x, -z}}; }

class TrackProjector {
 public:
  void project(std::span<TrackView> views, const ScenarioProcessor* processor);
 private:
  std::unordered_map<TrackKey, History, TrackKeyHash> history_;

```

The frame tags of §15 make `P_W = pose.position + R_WR * L` type-check only with a `RadarPoint`
on the right-hand side.

One owner of the scenario, the processor, the RDP client, the projector, the layers, the

## 29. Live clock and replay

`std::chrono::steady_clock` for wall time; the anchor is `(newestPacketTimeMs, steadyAtArrival)`
and the displayed time is `min(anchor + elapsed, anchor + maxLead)`, clamped to the export span,
never running backwards except on a detected restart (> `restartJump`). `replayMode` switches to
export playback at the chosen rate; `goLive()` returns. Identical rules to §18 of the
architecture document, because the behaviour is the contract.

## 30. Rendering backend evaluation

| Option | For | Against | Verdict |
|---|---|---|---|
| **VTK 9 C++ with `QVTKOpenGLNativeWidget`** | same scene graph, same visual result, mature picking, the Python scene ports almost line for line | heavy dependency, VTK's own render loop must be driven carefully (the double-render lesson applies) | **chosen for 3D** |
| Qt3D | Qt-native, ECS | thin ecosystem, poor large-line-set performance, uncertain future | no |
| Custom QRhi / OpenGL | smallest dependency, full control of the frame | months of work to reach parity (picking, text, translucency) | no |
| `QGraphicsView` / custom `QPainter` | native, fast for 2D, precise control of labels | 2D only | **chosen for 2D and PPI** |

2D and the PPI leave pyqtgraph behind: a `QGraphicsScene` with custom items, or direct `QPainter`
painting of a scene description, removes the tick-level trap of §24 of the architecture document
and gives exact control over label placement.

## 31. 3D view

Same scene, same update discipline:

* actors built once; per frame only `vtkProp3D::SetUserMatrix` and point arrays change;
* beam geometry updated in place (same topology);
* trails as one `vtkPolyData` per layer with per-point colours;
* **one render request per frame** — the double-render defect must not be reintroduced; a debug
  counter on `vtkRenderer::StartEvent` is part of the test suite;
* sensor-versus-fused weights, the ring, the label and the fade are the values in
  `render/style.h`, ported from the Python constants.

## 32. 2D view and Aircraft PPI

A shared `SceneModel` (positions, symbols, colours, labels for one frame) is produced by
`render/`, and two painters consume it: the Cartesian ENU map and the aircraft-frame PPI (0° =
nose, clockwise). Painting is a flat loop over arrays with `QPainter::drawPixmapFragments` for
symbols; labels go through the placement pass of §34.

## 33. Visual style, symbols and labels

`render/style.h` is the single definition, as today: classification → colour, source → shape,
with the fused/sensor weights and the classification palette kept away from the ownship, vector
and sensor colours. Symbols are pre-rendered into a `QPixmap` atlas at start-up and per device
pixel ratio. Label text comes from real identifiers only
(`T<TgtId>`, `FUSED-<systemTrackId>`, `S<sensorId>-ST<systemTrackId>`).

## 34. Interaction, picking and selection

* Picking projects candidate world points with the camera's composite projection matrix and
  takes the nearest within a pixel radius, markers before trajectory points — the same algorithm
  as `view_3d::_project` / `_pick_at`, which avoids VTK's hardware picker entirely.
* Click selects, click on empty space clears, double click focuses the camera and releases
  Follow, hover shows details.
* Label decluttering: project all visible labels, keep the topmost, step colliding ones down one
  line — `stacked_offsets` ported as a pure function so it keeps its unit tests.
* Camera presets and their shortcuts (`O C T S B N R`, `D` for DEBUG) are a table, not a switch.

## 35. Widgets, layout, configuration and audio

* Layout as today: header, status line, navigation panel, one world view (3D or 2D) with the
  playback bar, PPI and ownship panel on the right, Track Details at the bottom.
* Track Details is a `QAbstractTableModel` + `QTableView` with a proxy for sorting — the current
  table's refresh rate cap (5 Hz) stays.
* Configuration: the same `display_config.json`, parsed with `QJsonDocument` into a strongly
  typed `Config` struct, with every field validated at start-up and an explicit error listing
  unknown or malformed keys.
* Audio: `QSoundEffect`, one instance, started/stopped by 3D visibility, failing silently to a
  warning.

## 36. Testing, performance budget and packaging

**Testing.** Per-module test targets; the geometry tests are direct ports (they are the contract);
golden-data tests replay a recorded packet stream and a small export and compare the produced
`FrameState` / `TrackView` values against fixtures captured from the Python application. A GUI
smoke test drives the real window with `QTest`.

**Performance budget** (1700×1000, the reference scenario):

| Stage | Budget |
|---|---|
| 3D frame, GUI thread | ≤ 8 ms (Python: 15–20 ms) |
| 2D/PPI repaint | ≤ 5 ms (Python: 11 ms) |
| VTK renders per frame | 1.00 |
| Packet decode | ≤ 2 µs per datagram |
| Warm start to first frame | ≤ 3 s (Python: 17 s) |
| Allocations in the render path | 0 |

**Packaging.** `windeployqt` + the VTK DLLs into a versioned folder, or a single MSI. No Python
runtime.

## Implementation phases

Each phase ends with its tests passing and a reviewable artefact. Nothing in the Python
application, the RDP or the radar code is touched in any phase.

| # | Phase | Ends when |
|---|---|---|
| 1 | Skeleton: CMake, presets, vcpkg manifest, empty targets, CI | `ctest` runs on an empty suite in CI |
| 2 | `core`: units, frame tags, geometry, attitude, coordinates, kinematics | the ported geometry tests pass, including the eight attitudes |
| 3 | `rdp/packet`: decoder + rejection reasons | byte-for-byte round trip against captured datagrams |
| 4 | `rdp/track_store`: lifetime, restart, statistics | store tests pass against a recorded stream |
| 5 | `rdp` receiver: `QUdpSocket` worker, batching, bind retry | a replayed stream is counted correctly, no GUI |
| 6 | `export`: types, parser, binary cache | the reference export loads; values match the Python arrays |
| 7 | `processing`: scenario processor + frame types | `FrameState` matches Python fixtures at sampled times |
| 8 | `processing`: track projector | the 1e-6 m round trip passes; placement matches fixtures |
| 9 | `app`: `AppState`, live clock, configuration | headless replay reproduces LIVE/STALE transitions |
| 10 | `render` + `ui` 3D: scene, camera, one-render discipline | the ownship, sensors and beam render; render counter = 1 |
| 11 | 3D tracks, targets, trails, labels, decluttering | visual parity with the Python screenshots |
| 12 | 2D view and PPI on the shared `SceneModel` | parity, and the paint budget met |
| 13 | Panels, table, status, pop-out, hover, audio | GUI smoke test passes |
| 14 | Parity gate, profiling, packaging | golden-data parity, §36 budgets met, deployable build |

A port is only worth starting if phases 1–9 can be completed and pass the parity gate; the UI
phases are the cheap part.
